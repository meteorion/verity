# 查询改写与相似问法处理优化方案

> 状态：设计阶段 · 未实现  
> 关联模块：`app/retrieval/hybrid.py` · `app/graph/nodes/generate.py` · `app/graph/nodes/` · `app/inference/llm.py`

---

## 1. 问题定义

用户的原始查询往往不是信息检索的最优形式，主要表现为：

| 问题类型 | 示例 | 影响 |
|---|---|---|
| 口语化/省略 | "这个怎么退？" | 向量距离大，召回失败 |
| 上下文依赖（指代） | "上次说的那个功能" | 离开对话历史无法理解 |
| 多跳问题 | "A 产品的退款规则和 B 产品有什么不同？" | 单次检索无法覆盖全部子问题 |
| 表述多样 | "能退货吗" / "支持换货么" / "七天无理由" | 同意不同形，语义相近但词不重叠 |
| 噪声/错别字 | "退完款会不会影响我的芝麻分" | 相关词被干扰 |

## 2. 查询改写（Query Rewriting）

### 2.1 上下文感知改写（Coreference Resolution）

**问题**：多轮对话中，用户查询含有指代词（"它"、"这个"、"上面说的"）或省略主语，单轮检索无法处理。

**方案**：在 RAG 检索前，用 LLM 将查询与近 N 轮对话历史合并，生成一个**自包含的独立问题**。

```
对话历史：
  U: 你们有退款政策吗？
  A: 有，支持7天无理由退款...
  U: 那换货呢？              ← 原始查询，省略了主语"退款/产品"

改写后：
  "你们支持换货吗？换货的政策是什么？"
```

**实现位置**：在 `hybrid_retrieve()` 调用之前，新增 `rewrite_query(query, history)` 步骤。

**触发条件**：
- 查询长度 < 10 字，且
- 对话历史轮数 ≥ 1，且
- 查询中含有指代词（"它"、"这"、"那"、"上面"、"刚才"等）或疑问词开头（"那"、"还有"）

不满足上述条件时跳过改写，避免无谓的 LLM 调用。

**Prompt 模板**：
```
你是一个查询改写助手。根据对话历史，将用户最新的问题改写为一个可以独立理解的完整问题。
只输出改写后的问题，不要解释。如果问题已经完整，原样输出。

对话历史：
{history}

用户最新问题：{query}

改写后的问题：
```

### 2.2 多查询展开（Multi-Query）

**问题**：用户表述可能不是检索知识库的最优角度，单一查询存在召回盲区。

**方案**：用 LLM 将原始查询改写为 N 个不同角度的子查询，分别检索后合并去重。

```
原始查询："换货流程"

展开为：
  1. "如何申请换货？"
  2. "换货需要什么条件？"
  3. "换货需要多少天？"
  4. "换货和退货有什么区别？"

各子查询独立检索 → RRF 合并结果
```

**实现要点**：
- N 默认为 3（超过 3 个子查询的边际收益递减，且延迟线性增加）
- 子查询检索**并行**执行（`asyncio.gather`）
- 合并时用 RRF 再次融合，去重以 `chunk_id` 为键
- 仅对复杂问题启用（查询含连词"和"/"与"/"或"，或长度 > 20 字）

**延迟代价**：+1 次 LLM 调用 + N 次并行检索。若并行良好，总延迟约增加 300-500ms。

---

### 2.3 Step-Back Prompting（后退提问）

**问题**：用户问的是具体细节，但知识库里存储的是通用原则，向量距离远。

**方案**：将具体问题"后退"为更通用的父问题，用父问题检索通用知识，再用具体问题检索细节，合并两次结果。

```
具体问题："我买的 X500 型号在新疆可以退货吗？"

后退问题："退货的地区限制政策是什么？"

检索策略：
  后退问题检索 → 获取通用政策 chunk
  + 原始问题检索 → 获取产品/地区特殊规则 chunk
  合并送给 LLM
```

**触发条件**：查询中含有具体的专有名词（产品型号、地名、人名）时启用。

---

### 2.4 查询规范化（Normalization）

轻量级预处理，不需要 LLM 调用：

1. **错别字纠正**：接入阿里云文字识别/百度 AI 开放平台 Text Correction API，或本地词典替换常见错别字（"退完"→"退款"，"发票报销"→保留）
2. **同义词扩展**：维护领域同义词表（`config/synonyms.json`），查询时对关键词做同义词替换
   ```json
   { "退货": ["退款", "7天无理由", "换货"], "发票": ["收据", "开票"] }
   ```
3. **停用词过滤**：移除"我想知道"、"请问"、"能不能告诉我"等无信息量前缀
4. **数字/单位规范化**："七天" → "7天"，"一百元" → "100元"

## 3. 相似问法处理（Similar Question Handling）

### 3.1 语义缓存（Semantic Cache）

**现状**：`SEMANTIC_CACHE_THRESHOLD=0.93` 已有配置，但实现状态待确认（`app/api/chat.py` 中暂未看到实际调用）。

**完整方案**：
```
用户查询 Q
  → 对 Q 做 embedding → 向量 v
  → 在 Redis 中查找与 v 余弦相似度 ≥ 0.93 的历史查询
  → 命中：直接返回缓存的回答（跳过检索和 LLM）
  → 未命中：正常走 RAG 流程，执行后将 (v, answer) 写入 Redis（TTL=24h）
```

**存储结构**：
- Key: `semantic_cache:{hash(v)}`
- Value: `{"query": str, "answer": str, "chunks": [chunk_id...], "ts": int}`
- 用 Redis 的 `HSET` + 自定义相似度扫描，或引入 Redis Stack（内置向量搜索）

**缓存失效策略**：
- TTL 24 小时（防止过期知识库内容被缓存命中）
- 知识库更新（文档导入/删除）时清空相关 product_line 的缓存条目
- 管理后台提供"清空全部缓存"按钮

---

### 3.2 FAQ 精确匹配层

**问题**：高频标准问答（FAQ）每次都走向量检索浪费资源，且存在边界相似问法"擦边"到错误 FAQ 的风险。

**方案**：维护一张 `faq_questions` 表，每条 FAQ 存储问题的 embedding；用户查询先过 FAQ 层：

```
查询 → 与 FAQ embedding 库做相似度匹配
  → 相似度 ≥ 0.96：直接返回 FAQ 答案（不走 RAG）
  → 0.80 ≤ 相似度 < 0.96：FAQ 答案作为"候选上下文"注入 RAG 检索结果
  → 相似度 < 0.80：正常 RAG
```

**数据管理**：管理后台新增 FAQ 维护页面（可在 KnowledgeBase 页面下新增 tab），支持批量导入问答对。

---

### 3.3 多问法扩充索引（Question Augmentation）

**问题**：知识库中存储的是"答案文本"，但用户提问角度各异，标准答案文本与用户问法的向量距离可能较大。

**方案**：文档导入时，为每个 chunk 用 LLM 生成 K 个可能的用户问法，将这些问法的 embedding 与 chunk 关联存储。

```
chunk 内容："退款将在3-5个工作日内原路返还至您的支付账户。"

生成问法：
  1. "退款多久到账？"
  2. "申请退款后几天能收到钱？"
  3. "退款会退到哪里？"
  4. "退款到账时间"

将以上4个问法的 embedding 分别存入 question_embeddings 表，关联同一个 chunk_id
检索时同时查 chunk_embeddings 和 question_embeddings，取并集
```

**存储设计**：
```sql
CREATE TABLE question_embeddings (
    id          BIGSERIAL PRIMARY KEY,
    chunk_id    TEXT NOT NULL REFERENCES chunks(chunk_id) ON DELETE CASCADE,
    question    TEXT NOT NULL,
    embedding   vector(1024),
    created_at  TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX ON question_embeddings USING hnsw (embedding vector_cosine_ops);
```

**成本**：每个 chunk 生成 K=4 个问法，文档导入时一次性付出，不影响检索延迟。

---

### 3.4 意图感知检索路由

**问题**：不同意图的查询对检索策略的需求不同。

**方案**：intent 节点分类结果注入检索参数：

| 意图 | 检索策略 |
|---|---|
| `faq` | 优先 FAQ 精确匹配 → 语义缓存 → RAG |
| `product_inquiry` | 启用元数据过滤（product_line）+ 多查询展开 |
| `after_sales_refund` | 启用 Step-Back + 时效过滤（最新政策优先） |
| `complaint` | 跳过 RAG，直接转人工（检索投诉处理规范作为参考） |
| `chitchat` | 跳过 RAG，直接 LLM 生成 |

**实现**：在 `graph/nodes/generate.py` 的 `_rag_retrieve()` 中根据 `state["intent"]` 动态选择检索策略。

## 4. 整体流程架构

```
用户输入 query
    │
    ├─ [预处理] 规范化 / 错别字纠正 / 停用词过滤
    │
    ├─ [语义缓存] 命中 → 直接返回
    │
    ├─ [FAQ 精确匹配] 命中(≥0.96) → 直接返回
    │                命中(0.80~0.96) → 结果注入后续检索
    │
    ├─ [查询改写]
    │     ├─ 上下文感知改写（多轮指代解析）
    │     ├─ 多查询展开（复杂问题）
    │     └─ Step-Back（含专有名词）
    │
    ├─ [意图路由] 选择检索策略
    │
    ├─ [混合检索] dense + sparse + question_embeddings
    │
    ├─ [精排] reranker（P2）
    │
    └─ [生成] LLM 生成回答
```

## 5. 实现优先级

| 优先级 | 方案 | 实现难度 | 预期收益 |
|---|---|---|---|
| P1 | 2.4 查询规范化 | 低 | 低（基础保障） |
| P1 | 2.1 上下文感知改写 | 中 | 高（多轮场景必需） |
| P1 | 3.1 语义缓存落地 | 中 | 高（降本 + 提速） |
| P2 | 3.2 FAQ 精确匹配层 | 中 | 中 |
| P2 | 2.2 多查询展开 | 中 | 中 |
| P2 | 3.4 意图感知检索路由 | 中 | 中 |
| P3 | 3.3 多问法扩充索引 | 高 | 高（但成本高） |
| P3 | 2.3 Step-Back Prompting | 中 | 中（场景有限） |

## 6. 评估方案

每项优化上线前后对比以下指标（在同一评估数据集上）：

| 指标 | 工具 | 说明 |
|---|---|---|
| `context_recall` | Ragas | 改写后是否召回了正确 chunk |
| `answer_correctness` | Ragas | 最终回答质量 |
| P95 延迟 | 压测日志 | 改写引入的延迟代价 |
| 缓存命中率 | Redis INFO | 语义缓存实际收益 |
| LLM 调用次数 | 埋点统计 | 成本变化 |
