严格按照以下 RAG 文档标准对内容进行重写和结构化处理。

## 🎯 RAG 文档重写规范

### 1. 严格的层级标题结构（Heading Hierarchy）
- **必须有且仅有一个 H1 标题**：正文的**第一行必须是 `# 文档核心标题`**。
- **禁止跳级**：严格按照 `#` -> `##` -> `###` 递进。
- **标题必须自包含（Self-contained）**：每个标题必须包含足够的上下文，确保在脱离父级标题时依然具有明确的检索意义。
  - ❌ 错误示范：`### 邮件规范`
  - ✅ 正确示范：`### 代理商层级申请报备邮件规范`

### 2. 结构化正文内容（Structured Body）
- **列表化**：步骤、条件、优缺点等必须使用无序（`-`）或有序（`1.`）列表，拒绝大段长句。
- **表格化**：涉及对比、参数、价格、规格、邮件收发人等结构化数据时，必须转换为 Markdown 表格。
- **重点加粗**：对核心概念、专有名词、关键警告使用加粗（`**text**`）处理。

### 3. 显式问答对（Q&A / FAQ 格式）
- 若原文包含常见问题，统一转化为 `### 问：[具体问题]` 和 `答：[详细解答]` 的格式，确保分块时的语义完整性。

### 4. 上下文关联与去噪（Context & Clean-up）
- 剔除原文中无意义的免责声明、冗长版权声明、广告推广等噪声信息。
- 遇到生僻缩写或内部黑话，使用括号或脚注（`[^1]`）进行解释。

## 🚫 绝对禁止事项（Negative Constraints）
1. **禁止缺失 H1 标题**：正文必须以 `# ` 开头，绝对不能直接从 `##` 或 `###` 开始。
2. **禁止生成 YAML 元数据**：不需要在文档顶部生成 `---` 包裹的 Frontmatter 信息。
3. **禁止使用 Emoji 或特殊图标**：标题和正文中严禁出现 📈、📧 等表情符号，保持文本纯净。
4. **禁止使用代码块包裹纯文本**：除非是真正的编程代码，否则邮件模板、话术模板等必须使用普通文本或引用（`>`）格式，严禁使用 ```text 包裹。
5. **禁止使用无意义的废话标题**：如“一、背景”、“二、内容”、“三、注意事项”。
